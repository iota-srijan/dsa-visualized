Part 1 · Basics

Sorting a stack of exam papers with helpers

A teacher has 8 shuffled exam papers and wants them in order of marks. Sorting 8 at once is annoying. So the teacher splits the stack in half and hands each half to a helper.

Each helper follows the same rule: if your stack has more than one paper, split it and hand the halves to two more helpers. Someone handed a single paper just hands it straight back, because one paper is already "sorted".

Now the papers come back up the chain. Whenever you get two sorted stacks back, you combine them: look at the top paper of each stack, take the smaller one, place it on your output pile, and repeat. Because both stacks are already sorted, the smallest remaining paper is always on one of the two tops. You never need to look deeper.

That's the whole algorithm. Splitting is easy and dumb. Merging is where the order gets built.

Part 1 · Basics

Slow motion: merging two sorted piles

Master this one step and the rest of merge sort is just recursion. Each round: compare the two top cards, move the smaller one to the output. When one pile runs out, the other pile's leftovers go straight across, since they're already in order.

Count the comparisons: merging piles of size p and q takes at most p + q − 1 comparisons. Every card is touched once. That's why one merge is linear, O(n).

Part 2 · Core

The pseudocode, and how to remember it

Two functions. mergeSort only splits and delegates. merge does the sorting work. If you can write merge from memory, you can write the whole thing.

mergeSort(a, lo, hi):                 // sort a[lo..hi], both ends included
    if lo >= hi: return               // 0 or 1 item: already sorted (base case)
    mid = lo + (hi - lo) / 2          // split point
    mergeSort(a, lo, mid)             // helper 1 sorts the left half
    mergeSort(a, mid + 1, hi)         // helper 2 sorts the right half
    merge(a, lo, mid, hi)             // combine two sorted halves

merge(a, lo, mid, hi):
    copy a[lo..hi] into aux[lo..hi]   // spread both piles on the desk
    i = lo                            // top of left pile  (aux[lo..mid])
    j = mid + 1                       // top of right pile (aux[mid+1..hi])
    for k = lo to hi:                 // fill output slots left to right
        if i > mid:            a[k] = aux[j]; j++    // left pile empty
        else if j > hi:        a[k] = aux[i]; i++    // right pile empty
        else if aux[j] < aux[i]: a[k] = aux[j]; j++  // right top strictly smaller
        else:                  a[k] = aux[i]; i++    // left top smaller OR tie
Memory hook
"Split, split, stitch." Two recursive calls, then one merge.
Merge's 4 cases
"Left empty, right empty, right smaller, else left." Check the empty piles first, or you'll read past the end.
Recurrence
T(n) = 2·T(n/2) + n: two half-size problems plus a linear merge, which solves to O(n log n).
Part 2 · Core

Java, from clean to production-grade

Start with Classic. It's what you should be able to write on a whiteboard. The other tabs build on it.

import java.util.Arrays;

public class MergeSort {

    // Entry point: sorts the whole array.
    public static void sort(int[] a) {
        int[] aux = new int[a.length];   // one desk, reused by every merge
        sort(a, aux, 0, a.length - 1);
    }

    // Sort a[lo..hi] (both ends inclusive).
    private static void sort(int[] a, int[] aux, int lo, int hi) {
        if (lo >= hi) return;            // one paper: already sorted
        int mid = lo + (hi - lo) / 2;    // split the stack (overflow-safe)
        sort(a, aux, lo, mid);           // helper 1: left half
        sort(a, aux, mid + 1, hi);       // helper 2: right half
        merge(a, aux, lo, mid, hi);      // you: stitch them together
    }

    // a[lo..mid] and a[mid+1..hi] are each sorted. Make a[lo..hi] sorted.
    private static void merge(int[] a, int[] aux, int lo, int mid, int hi) {
        for (int k = lo; k <= hi; k++) aux[k] = a[k];   // spread piles on the desk

        int i = lo;          // finger on top of the left pile
        int j = mid + 1;     // finger on top of the right pile
        for (int k = lo; k <= hi; k++) {                  // fill output slots
            if      (i > mid)          a[k] = aux[j++];   // left pile empty
            else if (j > hi)           a[k] = aux[i++];   // right pile empty
            else if (aux[j] < aux[i])  a[k] = aux[j++];   // right top is smaller
            else                       a[k] = aux[i++];   // left smaller or tie (stable)
        }
    }

    public static void main(String[] args) {
        int[] a = {38, 27, 43, 3, 9, 82, 10};
        sort(a);
        System.out.println(Arrays.toString(a));  // [3, 9, 10, 27, 38, 43, 82]
    }
}
// No recursion. Start with n piles of size 1, then merge neighbours:
// size 1 -> 2 -> 4 -> 8 ... until one pile is left.
public static void sortBottomUp(int[] a) {
    int n = a.length;
    int[] aux = new int[n];
    for (int width = 1; width < n; width *= 2) {             // current pile size
        for (int lo = 0; lo < n - width; lo += 2 * width) {   // pair up neighbours
            int mid = lo + width - 1;                         // end of left pile
            int hi  = Math.min(lo + 2 * width - 1, n - 1);    // last pile may be short
            merge(a, aux, lo, mid, hi);                       // same merge as Classic
        }
    }
}
// Same O(n log n) time and O(n) space, but no call stack.
// The condition lo < n - width skips a lonely last pile with no partner;
// it just waits for a later, wider pass.
public class MergeSortFast {
    private static final int CUTOFF = 7;   // below this size, insertion sort wins

    public static void sort(int[] a) {
        int[] aux = new int[a.length];     // allocate ONCE, never inside recursion
        sort(a, aux, 0, a.length - 1);
    }

    private static void sort(int[] a, int[] aux, int lo, int hi) {
        // 1. Tiny piles: recursion overhead costs more than it saves.
        if (hi - lo + 1 <= CUTOFF) { insertionSort(a, lo, hi); return; }

        int mid = lo + (hi - lo) / 2;
        sort(a, aux, lo, mid);
        sort(a, aux, mid + 1, hi);

        // 2. Already in order? Biggest of left <= smallest of right: skip the merge.
        //    Makes already-sorted input run in O(n).
        if (a[mid] <= a[mid + 1]) return;

        merge(a, aux, lo, mid, hi);
    }

    private static void insertionSort(int[] a, int lo, int hi) {
        for (int i = lo + 1; i <= hi; i++) {
            int x = a[i];
            int j = i - 1;
            while (j >= lo && a[j] > x) { a[j + 1] = a[j]; j--; }   // strict > keeps it stable
            a[j + 1] = x;
        }
    }

    private static void merge(int[] a, int[] aux, int lo, int mid, int hi) {
        for (int k = lo; k <= hi; k++) aux[k] = a[k];
        int i = lo, j = mid + 1;
        for (int k = lo; k <= hi; k++) {
            if      (i > mid)          a[k] = aux[j++];
            else if (j > hi)           a[k] = aux[i++];
            else if (aux[j] < aux[i])  a[k] = aux[j++];
            else                       a[k] = aux[i++];
        }
    }
}
// Java's own Arrays.sort(Object[]) uses TimSort, which takes these ideas further:
// it finds already-sorted "runs" in the input and merges those.
import java.util.Comparator;

public class GenericMergeSort {

    public static <T> void sort(T[] a, Comparator<? super T> cmp) {
        T[] aux = a.clone();                       // same type and length, no unchecked cast
        sort(a, aux, 0, a.length - 1, cmp);
    }

    private static <T> void sort(T[] a, T[] aux, int lo, int hi, Comparator<? super T> cmp) {
        if (lo >= hi) return;
        int mid = lo + (hi - lo) / 2;
        sort(a, aux, lo, mid, cmp);
        sort(a, aux, mid + 1, hi, cmp);
        merge(a, aux, lo, mid, hi, cmp);
    }

    private static <T> void merge(T[] a, T[] aux, int lo, int mid, int hi, Comparator<? super T> cmp) {
        for (int k = lo; k <= hi; k++) aux[k] = a[k];
        int i = lo, j = mid + 1;
        for (int k = lo; k <= hi; k++) {
            if      (i > mid)                            a[k] = aux[j++];
            else if (j > hi)                             a[k] = aux[i++];
            else if (cmp.compare(aux[j], aux[i]) < 0)    a[k] = aux[j++];   // strictly less
            else                                         a[k] = aux[i++];
        }
    }

    record Student(String name, int marks) {}

    public static void main(String[] args) {
        Student[] s = {
            new Student("Asha", 72), new Student("Ravi", 85), new Student("Meera", 72),
            new Student("Kabir", 60), new Student("Dev", 85), new Student("Zoya", 72)
        };
        sort(s, Comparator.comparingInt(Student::marks));
        // Kabir 60, Asha 72, Meera 72, Zoya 72, Ravi 85, Dev 85
        // Equal marks keep their original order. That's stability.
    }
}
// An inversion is a pair (i < j) with a[i] > a[j]. It measures "how unsorted" an array is.
// Brute force is O(n^2). Merge sort counts them in O(n log n) with ONE extra line.
static long countInversions(int[] a, int[] aux, int lo, int hi) {
    if (lo >= hi) return 0;
    int mid = lo + (hi - lo) / 2;
    long count = countInversions(a, aux, lo, mid)
               + countInversions(a, aux, mid + 1, hi);

    for (int k = lo; k <= hi; k++) aux[k] = a[k];
    int i = lo, j = mid + 1;
    for (int k = lo; k <= hi; k++) {
        if      (i > mid)         a[k] = aux[j++];
        else if (j > hi)          a[k] = aux[i++];
        else if (aux[j] < aux[i]) {
            a[k] = aux[j++];
            count += mid - i + 1;   // this right card jumps ahead of EVERY card still in the left pile
        }
        else                      a[k] = aux[i++];
    }
    return count;
}
// {2, 4, 1, 3, 5}  ->  3 inversions: (2,1), (4,1), (4,3)

Part 3 · Analysis

Why it's n log n, as a picture

Look at the recursion tree as rows. Every row contains all n items, just chopped into smaller piles. Merging every pile in one row touches each item once, so each row costs n.

How many rows? Each split halves the pile size, and you can halve 8 only 3 times before you hit 1 (8 → 4 → 2 → 1). That's log₂ n rows. Rows × cost per row = n · log₂ n. And this never changes with the input: sorted, reversed, or random, it always does the same splits.

For n = 8: 3 rows of merging × 8 items each = 24 units of work. Insertion sort's worst case is about 8²/2 = 28. Small n, small difference. Now drag the slider.

Part 4 · Advanced

Stability: who goes first on a tie?

Back to exam papers. Asha, Meera and Zoya all scored 72, and they handed in their papers in that order. A stable sort keeps them in that order after sorting by marks. An unstable sort might shuffle them.

Why care? Because it lets you sort in layers. Sort by name first, then stably by marks, and students with equal marks stay alphabetical. Java relies on this: Collections.sort and Arrays.sort(Object[]) are guaranteed stable because they're merge-based.

Part 4 · Advanced

Variants and tuning tricks

Bottom-up
Skip recursion entirely: merge piles of size 1, then 2, then 4. Same cost, no stack. Switch the visualizer to Bottom-up mode to see it. Its tree grows from the leaves up.
Insertion-sort cutoff
For piles of ~7–15 items, insertion sort is faster than more recursion. Most real implementations switch over. Typically 10–20% faster.
Skip sorted halves
If a[mid] <= a[mid+1], the two halves are already in order. Skipping the merge makes sorted input linear.
Allocate aux once
Create the scratch array in the entry method and pass it down. new int[] inside every call is the most common performance bug.
Linked lists
Merge sort is the go-to for linked lists: merging just relinks nodes, so extra space drops to O(1) besides the stack. (LeetCode 148 "Sort List".)
External sort
Data bigger than RAM? Sort chunks that fit in memory, write them to disk, then merge the sorted files. Databases do this for big ORDER BY queries.
TimSort
Java (objects) and Python's default sort. A merge sort that detects existing sorted runs and uses insertion sort for short ones. It's fast on real-world, partly-sorted data.
Parallel
The two halves are independent, so they can run on different threads. Arrays.parallelSort does this with the fork/join pool.

The one gotcha worth remembering

The tie rule decides stability, and the bug is invisible

Wrong intuition: "< vs <= doesn't matter, the output is sorted either way." The output is sorted either way. That's exactly why the bug slips through tests on plain int arrays. It only bites when you sort objects by one field and expect equal items to keep their order.

✗ Unstable
// takes RIGHT on a tie
else if (aux[j] <= aux[i]) a[k] = aux[j++];
else                      a[k] = aux[i++];
✓ Stable
// takes LEFT on a tie
else if (aux[j] < aux[i])  a[k] = aux[j++];
else                      a[k] = aux[i++];

Rule: on a tie, the left pile wins, because left items came first in the original array. Equivalent form if you compare the other way: if (aux[i] <= aux[j]) take left.

Other traps, in order of how often they happen

  1. Mixing inclusive and exclusive bounds. Pick one convention (this page uses a[lo..hi] inclusive) and stick to it. With exclusive hi, the base case becomes hi - lo <= 1 and the right half starts at mid, not mid + 1. Mixing them gives infinite recursion or skipped items.
  2. Allocating new int[] inside merge. Correct, but creates garbage for every call. Allocate aux once.
  3. Forgetting the leftovers. In the "two while loops" style of merge, people stop when one pile empties and forget to copy the rest of the other pile. The 4-case loop above handles it automatically.
  4. mid = (lo + hi) / 2 overflow. If lo + hi exceeds about 2.1 billion it wraps negative. lo + (hi - lo) / 2 can't overflow. This was a real bug in Java's own binary search for years.
Test yourself · answer out loud before you open each one

Quick recall check

1. Why is a single item "already sorted", and why does the algorithm need that fact?

There's nothing to compare it with, so no order can be wrong. It's the base case: without it, the recursion would keep splitting forever. Every merge in the algorithm ultimately starts from these one-item piles.

2. In merge, why do you only ever compare the two TOP items?

Both piles are sorted, so each pile's smallest remaining item is its top. The overall smallest remaining item must be one of those two tops. Nothing deeper can beat them.

3. Trace it: what does [38, 27, 43, 3, 9, 82, 10] look like right after the very first merge?

[27, 38, 43, 3, 9, 82, 10]. Top-down goes left-first all the way down, so the first merge is a[0..1] = (38, 27) → (27, 38). Check it in the visualizer with "Your own numbers".

4. Why does the recursion tree have about log₂ n levels?

Each level halves the pile size. Starting from n, the number of halvings until you reach 1 is log₂ n. With n = 1,024 that's only 10 levels.

5. You change aux[j] < aux[i] to aux[j] <= aux[i]. Does it still sort? What breaks?

It still sorts correctly. It loses stability: on a tie it takes the right item first, so equal items can swap their original order.

6. Why does Java use quicksort for int[] but a merge sort (TimSort) for Object[]?

Two equal ints are indistinguishable, so stability is meaningless and quicksort's lower memory use and speed win. Objects with equal keys are different objects, so stability matters, and merge sort guarantees it.

7. Write merge's four cases from memory, in order.

Left pile empty → take right. Right pile empty → take left. Right top strictly smaller → take right. Otherwise (left smaller or tie) → take left.
